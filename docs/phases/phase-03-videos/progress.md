### SI-03.5 — Upload Completion Notification Consumer
- **Status:** completed
- **Tests:** 3 passing (integration, real Redis + Bull + MinIO)
- **Observations:**
  - TD-02 left the delivery mechanism as "channel/list" (deliberately undetermined). Resolved concretely as MinIO's `access` notification format: `RPUSH` onto a Redis **list**, consumed via `BLPOP` — MinIO's `namespace` format (hash-mirroring) doesn't fit an event-stream consumer. `MINIO_NOTIFY_REDIS_*_PRIMARY` env vars added to the `minio` service in `compose.yaml`; `minio` now `depends_on: redis: condition: service_healthy`.
  - The actual Redis-list payload shape does **not** match the plan's illustrative `{ EventName, Key, Records }` example. Verified empirically (manual `putObject` + `redis-cli LINDEX`) against the real running MinIO container: each list entry is `JSON.stringify([{ Event: [<S3 event record>], EventTime }])` — a JSON array wrapping one `{ Event, EventTime }` object, where `Event[0]` is the actual S3-style record (`eventName`, `s3.object.key`, etc.). `object.key` is URL-encoded (`decodeURIComponent` applied). Implemented and confirmed against real infrastructure rather than trusting secondary sources, since official docs were thin/redirected on this exact wire format.
  - Bucket-level event subscription (the `mc event add` equivalent) is done programmatically via the `minio` JS SDK's `setBucketNotification`/`QueueConfig`/`buildARN` in `StorageModule.onModuleInit` (which already owned bucket-existence per SI-03.4) rather than a manual `mc` CLI step — keeps all MinIO bootstrapping in application code, idempotent on every restart (full replace, not append).
  - `ioredis` (already an indirect dependency via `bull`) was promoted to a direct `package.json` dependency since `UploadNotificationListener` imports it directly for the dedicated BLPOP subscriber connection (Bull's own Redis connections are occupied by queue operations, not general-purpose pub/sub or list ops).
  - `UploadNotificationListener` is registered in `VideosModule`, which both `AppModule` (API) and `WorkerModule` (worker) import — so both containers run a BLPOP consumer against the same list. This is harmless (not a bug): `BLPOP` pops atomically, so exactly one process handles each notification; both write to the same Postgres DB via equivalent `VideosService` instances. Restricting the listener to only one of the two containers was not requested by the plan and was not pursued as an SI-03.5 scope change.
  - Verified the full pipeline end-to-end manually against real infrastructure (not just the automated test, which exercises `markProcessing` directly): inserted a real draft `Video` row, `PUT` the matching object key via the `minio` SDK, confirmed the row transitioned to `processing` in Postgres with no listener errors in `docker compose logs worker`.
  - Consequential fix in `videos.service.integration-spec.ts` (SI-03.4 file): removed an unused `MINIO_CLIENT` import and typed a `job.data` access — both introduced/exposed by this SI's new test cases — to keep the file `npm run lint` clean. Pre-existing lint debt in unrelated SI-03.4/auth files (unbound-method, unsafe-any patterns) was left untouched as out-of-scope for this SI.

### SI-03.6 — Video Processor Worker (Metadata Extraction and Thumbnail Generation)
- **Status:** completed
- **Tests:** 2 passing (integration, real ffprobe/ffmpeg via execa against a generated fixture + a corrupt-content fixture)
- **Observations:**
  - **TD-08 revised: `execa` downgraded from `^10.x` to `^5.x`.** `execa@^10.x` (as originally decided) is pure-ESM; one of its transitive dependencies (`unicorn-magic`, via `npm-run-path`) ships a `package.json` with no `require` export condition at all. Real Node (v22+/v25+) resolves this transparently via native `require(esm)` — confirmed working in production/`ts-node` execution — but Jest 30's module resolver does not replicate that capability; this is a resolution failure (no matching export condition), not a transform/syntax issue, so no `transformIgnorePatterns` configuration can fix it. Root-caused by direct reproduction (identical code succeeds under `ts-node`, fails under Jest) before escalating to the user via AskUserQuestion with three options (downgrade execa / migrate Jest to native ESM / mock execa in the test); user selected the downgrade. `execa@^5.x` is the last CJS-native major (pre-ESM migration at v6.0.0), has a fully Jest-resolvable dependency tree, and preserves TD-08's original rationale (actively-used, structured-error wrapper, not `fluent-ffmpeg`). API shape differs from v10: v5 uses a default export (`import execa from 'execa'`, not `{ execa }`) and `ExecaError` is a type-only interface with no runtime class — failure detection uses `error instanceof Error && 'stderr' in error && 'exitCode' in error` instead of `instanceof ExecaError`. TD-08 and `library-refs.md` updated with a Revisions entry recording this.
  - **MinIO SDK's `fGetObject`/`fPutObject` avoided in favor of `getObject`/`putObject` + manual stream piping.** Independently of the execa issue, `Client.fGetObject` was found to fail deterministically under Jest (`ENOENT` on its internal `.part.minio` temp file, immediately after its own write-stream pipeline resolved) while working correctly under plain Node/`ts-node` — root-caused via a minimal reproduction (raw `fs.createWriteStream` + `pipeline` + `fs.stat` succeeds under Jest; MinIO's own `fGetObject` fails under Jest but succeeds under `ts-node`; a hand-replay of `fGetObject`'s exact internal logic succeeds under Jest). Cause not fully isolated beyond "Jest-environment-specific interaction with MinIO SDK's internal partial-download resume logic" — not investigated further since a clean, equally-valid, better-tested alternative (`getObject` returning a stream + `stream/promises.pipeline` to a local file; `putObject` with a `Buffer`) sidesteps it entirely and is used in production code, not just the test.
  - **The new integration test runs via `docker compose exec worker`, not `nestjs-api`.** `ffmpeg`/`ffprobe` binaries are only installed in the `worker` image (`Dockerfile.worker`, per SI-03.3) — `nestjs-api` doesn't have them. This is the first SI-03 test file that must be invoked against a different container than every prior test.
  - **Consequential fix to SI-03.5's integration test** (`videos.service.integration-spec.ts`, `markProcessing ... enqueues the process-video job`): now that `VideoProcessorService` is wired as a real consumer of the `video-processing` queue and the `worker` container runs it live, that pre-existing test started failing — it searched only the `waiting` job state, but the live consumer picks jobs up (moving them out of `waiting`) faster than the test's own follow-up query. Fixed by searching `['waiting', 'active', 'completed', 'failed']` instead of just `['waiting']`, which is robust regardless of whether a live consumer is running. Verified no data-corruption risk from the live worker's asynchronous, possibly-post-test-truncation `UPDATE` against the test's throwaway video row (TypeORM's `save()` on a pre-loaded entity issues a plain `UPDATE ... WHERE id`, a safe no-op against an already-truncated row — not a re-insert).
  - `VideoProcessorService` is registered in a new, dedicated `VideoProcessingModule` (not in `VideosModule`) so that only `WorkerModule` (which has the `ffmpeg`/`ffprobe` binaries) loads it — `AppModule`/`nestjs-api` never does. This differs from the plan's literal Technical action 5 wording ("register VideoProcessorService as a provider consumed by the worker bootstrap") only in mechanism (a small dedicated module vs. inline registration), for the same single-responsibility reason SI-03.5's `UploadNotificationListener` was placed in the shared `VideosModule` instead: here the dependency (ffmpeg/ffprobe binaries) is worker-only, so the module boundary enforces that instead of relying on convention.
  - Verified the full pipeline end-to-end manually against the real running `worker` container (not just the automated test): enqueued a real `process-video` job via a real Bull client against real Redis, confirmed the video row transitioned to `ready` with correct `duration_seconds`, `thumbnail_key`, and `file_size_bytes`, and confirmed the generated thumbnail object exists in MinIO.

### SI-03.7 — Endpoint GET /videos/:id/stream
- **Status:** completed
- **Tests:** 10 passing (unit=5, e2e=5, spec-derived from `nestjs-project/specs/videos-stream.plan.md`)
- **Observations:**
  - Added 3 new domain exceptions (`VideoNotFoundException` 404, `VideoNotReadyException` 409, `RangeNotSatisfiableException` 416) to `video.exception.ts`, matching the Error Catalog. `RangeNotSatisfiableException` isn't named in the SI's own Technical actions/ACs or the spec file, but it's the only sensible producer of the Error Catalog's documented `RANGE_NOT_SATISFIABLE` code — implemented (out-of-bounds/malformed `Range` header throws it) since leaving a documented error code with no code path would be an incomplete contract, but not given a dedicated automated test since neither the SI's Tests table nor the spec file asked for one.
  - `Content-Type` is hardcoded to `video/mp4` rather than read from a stored per-video content-type, since the `Video` entity has no such column and every stored object is always encoded as `.mp4` per TD-07's fixed `storageKey` convention (`channels/{channelId}/videos/{videoId}.mp4`) — there is no other value it could legitimately be.
  - `VideosService.streamVideo` uses `video.file_size_bytes` (populated by SI-03.6's worker) as the total-size source for both the `Content-Length`/`Content-Range` headers and range-bounds validation, avoiding an extra `statObject` round-trip to MinIO on every stream request.
  - `Range` parsing supports all three standard forms (`bytes=start-end`, `bytes=start-` open-ended, `bytes=-N` suffix) rather than only the fully-specified form the spec's one range scenario exercises (`bytes=0-1023`) — matches real browser/video-player seek behavior, which commonly sends open-ended ranges.
  - Controller uses `@Res()` with manual `status()`/`set()`/`.pipe()` (bypassing Nest's automatic response handling) since this is the project's first endpoint that streams a raw byte stream rather than returning a serializable value — no existing convention to mirror.
  - `@Public()` applied per the Authorization Matrix (anonymous playback/download, matching the project's "anonymous users watch freely" model) — the only `@Public()` route in `VideosController`.
